# 高频操作性能优化（2026-10-23）

上一次解决的是「打开一次要下多少东西」（首屏 1546KB → 238KB）。这次解决的是**用起来**的问题：切换难度、切换周、打字搜索、点排序、开弹窗、切页面——这些一天点几十上百次的操作，之前的每一次都在重算或重新下载。

## 结论

| 高频操作 | 之前 | 现在 |
| --- | --- | --- |
| 手机打字搜索（每键 p95，4× CPU） | 56ms（带筛选 40ms） | **16ms** |
| 桌面打字搜索 | 16ms | 16ms（已是计时器下限） |
| 打开分数分布弹窗（长任务，4× CPU） | 202ms | **50ms** |
| 切换页面（玩家/幻痛/我的/更新日志） | 首次点击现下载 5–133KB chunk | **0 下载**（空闲时已预取） |
| 切回刚看过的难度/周 | 发请求 + 骨架 + 270ms | **2ms 上屏，0 请求** |
| 切到没看过的难度 | 1 请求 270ms（网络决定） | 同左（网络决定，客户端≈20ms） |
| 首屏空闲期长任务 | 0 | 0（未引入新长任务） |

一句话：**客户端能消掉的都消掉了，剩下的 270ms 是源站往返，前端优化不动它。**

## 一、怎么测的

新建三个脚本，都是 mock 接口 + 固定 payload（`docs/perf/fixture-*.json`），排除源站抖动：

- `scripts/perf-interaction.mjs` — Event Timing（`durationThreshold: 16`）+ longtask + 帧间隔。结果 `docs/perf/interaction-<tag>.json`。
- `scripts/perf-usage.mjs` — 按 `API_DELAY`（默认 250ms）模拟真实往返，每个难度返回不同 payload（顶部玩家名带 `D{难度}·`），测「点击 → 新数据上屏」的端到端时间、请求数；手机场景用 CDP `Emulation.setCPUThrottlingRate(4)`。
- `scripts/perf-typing.mjs` — 逐个按键的 Event Timing 分布（p50/p95），模拟中端手机。

两个方法上的坑，记下来免得下次踩：

1. **headless 里的 rAF 帧间隔不可信**（要么 4.4ms 恒定，要么一个采样都没有）。判断流畅度只能用 longtask + Event Timing，别用帧率。
2. 第二个 `newContext` 的页面必须先 `bringToFront()`，否则 rAF/计时被节流，测出来全是假的。

## 二、瓶颈定位

1. **打字**：`useRankings` 的 `filtered` 是个大 `useMemo`，依赖 `searchQuery`，所以每敲一个字符就同步重跑「100 行 × 每行 3 个区 `zones.find` + `toLowerCase`」，然后整张虚拟列表重渲染。手机 4× CPU 下每键 56ms，超过 16ms 一帧，键盘明显发滞。
2. **切页**：四个页面都是 `React.lazy`，第一次点才下载。MinePage 66KB、ChangelogPage 133KB，点下去到看见内容要等下载 + 解析。
3. **分数分布弹窗**：为了画柱状图引了 `recharts`，单独一个 358KB（gzip 104KB）的 chunk，冷开时有 202ms 长任务（4× CPU）。
4. **切难度**：每次都是「骨架屏 → 等 270ms → 换内容」。同一难度第二次切回来还要再等（内存缓存 60s 后过期，且刷新页面就没了）。
5. **重试被缓存挡住**：错误横幅的「重试」调的是 `refresh()`，而 `refresh` 会命中 60s 内存缓存，导致点了没反应——看起来像"重试也没用"。

## 三、改了什么

### 1. 搜索/筛选走过渡渲染（`src/hooks/useRankings.js`）

```js
const deferredQuery = useDeferredValue(searchQuery);
const deferredFilters = useDeferredValue(charFilters);
```

输入框的值立刻更新（受控组件不受 defer 影响），列表过滤在过渡渲染里做，React 可以把一次长任务拆到多帧、并在有新输入时打断旧计算。

同时把每行的小写化结果预先存进 `searchIndex`（`Map<row, {name, id}>`，只在 `rawRankings` 变化时重建），过滤时不再对 100 行反复 `toLowerCase()`；空筛选值提前剔除（`activeFilters`）；`sortKey === null` 时直接 `slice(0, 100)`，不再先复制再排序。新增 `isFiltering` 供 UI 做"正在过滤"的轻提示（暂未使用）。

### 2. 分数分布弹窗去掉 Recharts（`src/components/Modals/BracketModal.jsx`）

这个图表本来就只有 10 根横条。改为复用页面已有的 `.bracket-list` 条形布局（div + 百分比宽度），加了「最多 X–Y · N 人」提示和峰值区间的绿色渐变高亮。**recharts 从产物里彻底消失**，`BracketModal` 这个 chunk 不再存在。

### 3. 空闲期预取四个页面（`src/App.jsx`）

首屏渲染完成后 `requestIdleCallback`（无该 API 时 setTimeout 1500ms 兜底）里 `import()` 四个页面 chunk。切页从"现下载"变成"已经在内存里"。省流量模式下（`navigator.connection.saveData`）或 2G 网络时跳过。

### 4. 战区数据两级缓存（`src/api/client.js`）

- **内存层**：原有 `Map`，补了 `CACHE_MAX = 48` 的插入序淘汰（之前永不淘汰）。
- **持久层**：`sessionStorage`，前缀 `huaxu_wz_cache_v1:`，索引 `huaxu_wz_cache_index`，TTL 10 分钟、最多 12 条、总字节上限 600KB，超限按最旧淘汰；隐私模式写失败静默降级。
- 新增 `peekWarzone(difficulty, week)` 返回 `{ data, age }`（内存优先 age=0，其次持久层），`fetchJson` 新增 `persist` 选项。

用 sessionStorage 而不是 localStorage：关掉标签页就清，不会让用户第二天看到昨天的榜单。

### 5. 缓存优先上屏 + 后台校验（`src/hooks/useWarzone.js`）

effect 开头先 `peekWarzone`：命中就**立刻**把数据落到状态里（不是骨架屏），然后

- 数据不到 60s → 完全不发请求；
- 超过 60s → 后台静默拉一次，成功后替换（stale-while-revalidate）。

这样"切回上一个难度"是 0 请求 + 2ms 上屏，而"放了一会儿再切回来"是先看见旧数据、再无声更新。30 分钟自动刷新同时改成 `document.hidden` 时不跑（后台标签页不白耗流量）。

### 6. 重试真的会重试（`RankingPanel.jsx`）

错误横幅的按钮从 `refresh` 换成 `refreshForce`（`forceRef` 绕过缓存），否则点重试会被本地缓存挡住。

## 四、复测数据

`node scripts/perf-typing.mjs`（4× CPU，手机视口）：

| 场景 | before p95 | after p95 |
| --- | --- | --- |
| 连打 10 个字符 | 56ms | 16ms |
| 带 3 个区 SSS+ 筛选再打字 | 40ms | 16ms |
| 清空输入 | 32ms | 16ms |

`node scripts/perf-usage.mjs`：

| 场景 | before | after |
| --- | --- | --- |
| 切难度（首次，API 250ms） | 269–287ms / 1 请求 | 270ms / 1 请求 |
| 切回缓存难度 | 19ms / 0 请求 | 2ms / 0 请求（跨页面刷新也可） |
| 分数分布弹窗冷开长任务 | 202ms | **50ms** |
| 切到「我的」页 | 新下载 66KB chunk | 0 |
| 切到「更新日志」页 | 新下载 133KB chunk | 0 |

`node scripts/perf-cache-check.mjs`（缓存语义）：

- 首次切英雄：274ms 上屏、1 请求
- 切回传奇：2ms、0 请求
- 等 65s（内存 60s 过期）再切英雄：1ms 上屏旧数据 + 后台 1 请求
- 手动刷新：强制 1 请求（不吃缓存）

构建产物：`index.js` 245.25KB（gzip 77.51）、`index.css` 90.96KB（gzip 15.44）；`BracketModal` chunk 消失。

## 五、还没做（按性价比排序）

1. **服务端缓存**（最大头，且不归前端管）：`api/*` 目前每次请求都回源，源站对某些难度会 20s+ 不返回。给 `/warzone/current/{d}` 加 `Cache-Control: s-maxage=30, stale-while-revalidate=120` 能让 Vercel 边缘直接扛住绝大部分请求，也是"切难度卡住"的根治办法。
2. **首屏再压**：首页 JS 245KB（gzip 77.5）里，MinePage/ChangelogPage 已经拆出去了，但 react + 业务逻辑还有空间——要动就得拆组件级，收益约 20–30KB，风险中等。
3. **角色图标仍是 1024 原图**：LazyImage 只减少了请求数（87→37），每张仍是 ~148KB。如果资源站支持带尺寸的路径（或能加个图片代理做缩放），可以再降一个数量级。
4. **快照/曲线采样**：现在随缓存数据一起跑，逻辑上无害（有 60s 去抖），但更干净的做法是只在网络成功时采样。
5. 移动端首行数据位置（现在 ~554px）属于布局阶段的事。
