# 低请求量性能优化方案（2026-10-19）

> 背景：源站 `api.huaxu.app` 是境外站点，请求过于频繁可能被限流/封禁。
> 目标：**在不牺牲体验的前提下，把对源站的请求次数降一个数量级**，同时解决卡顿。
> 结论：优先做“换轻量接口 + 历史批量 + 本地分级缓存 + 单飞/队列 + cron 降频”，预计典型访问从 **~70 次** 降到 **6–8 次**，cron 从 **768 次/天** 降到 **48–96 次/天**。

---

## 一、先看清：现在一次访问会打多少请求

| 场景 | 现在 | 说明 |
|---|---|---|
| 首页首访 | 1 | `warzone/current/16`（215KB） |
| 首页停留 1 小时 | 2–3 | 30 分钟自动刷新；切回页面重新 mount 再拉 |
| 切 5 个历史周 | 5 | 每周一次；60 秒后回来又重拉（历史周其实不会再变） |
| 玩家页（直接进入） | 1 + 1 + 最多 60 | 元数据 215KB + 玩家 69KB + 历史战绩每周最多 3 段位探测 |
| 玩家页开历届阵容 | +1 | `/players/{id}/warzone`（259KB） |
| 我的页首开 | 1 + 1 + 1 + 最多 40 | 战区元数据 + 幻痛 + 排名计算 + 回填/重算两条链路 |
| 幻痛页 | 1 | 31.7KB |
| GitHub Actions cron | **768/天** | 16 难度 × 48 次/天，固定 :00/:30，同一 IP 段连发 |

真正“显眼”的不是单个访客，而是 **cron 的固定节奏 + 历史战绩/我的页的瞬时连发**。

---

## 二、源站能力实测（决定方案的关键）

| 发现 | 实测 | 用法 |
|---|---|---|
| **轻量元数据接口** | `GET /servers/cn/warzone/current` → **2,546 字节**，含 `activities` + 当前周三区信息（无 rankings） | 替换玩家页/我的页为拿周范围而拉的 215KB 全量 |
| **幻痛轻量接口** | `GET /servers/cn/ppc/current` → **2,341 字节**，含各等级 boss 列表 | 我的页只要 boss 名，不必拉 31.7KB 榜单 |
| **玩家历届批量** | `GET /players/{id}/warzone` → **259KB / 1 次**，约 100 周上榜记录（含段位、排名、分数、三区、阵容） | **1 次替代历史战绩的 20–60 次探测**，还能复用给历届阵容 |
| **资源站有 WebP** | 同一路径 `.webp` 存在：角色头 1.03MB → **145KB**；辅助机 51KB → 13KB；头像框 65KB → 14KB | `getImageUrl` 改后缀即可，无需新增服务 |
| **无图片缩放** | `/cdn-cgi/image/...` 返回 404；`?x-oss-process`、`?imageMogr2`、`?w=` 均原图 | 缩略图需自建；先拿 WebP 的 7× 收益 |
| **Last-Modified 不可用** | 每次响应 `last-modified` = 当前时间；用 1 小时前的 `If-Modified-Since` 仍返回 200/215KB | **不要指望 304 省请求**；只能靠本地 TTL 缓存 |
| **CORS 允许条件头** | 预检允许 `if-modified-since`，但服务端时间戳使条件请求失效 | 同上 |
| **缓存头** | `Cache-Control: public, max-age=60`，无 `stale-while-revalidate` | 浏览器只在 60 秒内复用；60 秒后必回源 |

> 这解释了为什么“切页/切周”会反复打源站：浏览器缓存只有 60 秒，而历史周本可以永久缓存。

## 三、优化方案（按“对源站请求数”的收益排序）

### 3.1 请求层

#### ① 用轻量接口替换“顺手拉全量”（改动小、立刻生效）

- `PlayerPage` 只为 `activities` 拉 `/warzone/current/16`（215KB）→ 改 `/warzone/current`（2.5KB）。
- `MinePage` 同理；幻痛 boss 名改 `/ppc/current`（2.3KB）。
- 首页仍需要 rankings，保留 `/warzone/current/16`，但走下面的缓存。

**收益**：这两个页面每次进入少拉 **212KB**，请求数不变但负载降 99%；对源站更友好。

#### ② 历史战绩改批量接口（27 次 → 1 次）

`HistoryModal` 现在每周探测最多 3 个段位，20 周实测 17.6 秒 / 27 请求。
`src/api/history.js` 已有 `loadPlayerHistory()`，一次返回约 100 周，字段完全够用：

```
week / difficulty / rank / score / zones[{ id, name, score, characters }]
```

- 弹窗打开时先读 `localStorage` 反推缓存（6 小时），没有则拉一次；
- 结果按周渲染，不再逐周探测；
- 同一份数据同时供“历届阵容”使用，避免第二次 259KB。

**注意**：冷请求可能 30–60 秒（源站），要有进度提示；CDN 命中后 2–10 秒。

#### ③ 分级缓存：把“60 秒”变成“5 分钟 / 永久”

浏览器缓存只有 60 秒，应用层必须自己管。建议用 **IndexedDB**（单条 215KB，localStorage 5MB 放不下）：

| 数据类型 | TTL | 说明 |
|---|---|---|
| `/warzone/current` 元数据 | 6 小时 | 周切换时失效 |
| 当前周榜单 | 5 分钟 | 源站约 30 分钟更新，5 分钟足够新 |
| 历史周榜单 | **30 天 / 永久** | 已结算周不会变，永远不再回源 |
| 玩家资料 `/players/{id}` | 5 分钟 | 分数/排名会变 |
| 玩家历届 `/players/{id}/warzone` | 24 小时 | 含当前周，保守一点 |
| 角色详情 `/characters/{id}` | 7 天 | 基本不变 |
| 幻痛当前 | 5 分钟 | 与榜单同步 |

实现要点：

```js
// src/api/cache.js（示意）
const TTL = { meta: 6 * 3600e3, current: 5 * 60e3, history: 30 * 24 * 3600e3, player: 5 * 60e3, roster: 24 * 3600e3 };

export async function cachedJson(key, url, ttl, { force = false } = {}) {
    if (!force) {
        const hit = await idbGet(key);            // { body, at }
        if (hit && Date.now() - hit.at < ttl) return hit.body;
        if (hit) {
            // 过期：先返回旧数据（stale-while-revalidate），后台刷新
            refreshInBackground(key, url, ttl);
            return hit.body;
        }
    }
    return refresh(key, url, ttl);
}
```

配合 `useWarzone` 的初始 state 同步读内存镜像（模块级 `Map`），页面切换时先显示旧数据，再后台更新，不再闪骨架屏。

#### ④ 单飞 + 串行队列 + 退避（防止“瞬时连发”）

```js
const inflight = new Map();
export function once(key, fn) {
    if (inflight.has(key)) return inflight.get(key);
    const p = fn().finally(() => inflight.delete(key));
    inflight.set(key, p);
    return p;
}
```

所有对 `api.huaxu.app` 的 GET 走同一个队列：
- 两次请求间隔 **400–800ms 随机**；
- 失败（403/429/5xx）指数退避 1s→2s→4s…，最多 3 次；
- 连续失败 3 次熔断 10 分钟，期间只读缓存；
- 尊重 `Retry-After`（若有）。

这比“并发 20 个请求”更像正常用户，也避免被 Cloudflare 判定为爬虫。

#### ⑤ 跨标签页协调

同一浏览器开 3 个标签页，现在是 3 份轮询。用 `navigator.locks.request('huaxu-refresh', ...)` 或 `BroadcastChannel`：
- 只有一个 tab 真正发请求；
- 拿到新数据后广播 `{ key, at }`，其他 tab 从 IndexedDB 读。

#### ⑥ 我的页：两条链路合成一条

`MinePage` 的回填 effect（`478-513`）和重算 effect（`517-552`）都依赖 `[scores]`，同一周可能被请求两次：

- 合并成一个 effect、一次遍历；
- 用 `week` 做键去重，回填与重算共用同一份 `loadWarzone` 结果；
- 已补齐/已重算的周写 `sessionStorage` 标记，短期不再跑；
- `computeRankingGroups` 三区一次遍历，结果按 `week+zone` 缓存。

**收益**：首开“我的”页从最多 40 次降到 1–3 次。

#### ⑦ cron 降频与去节奏（最显眼的一项）

现状：每 30 分钟固定拉 16 个难度 = **768 次/天**，同一 GitHub IP 段、固定 :00/:30，且 16 个请求连续发出。

建议二选一：

| 方案 | 请求/天 | 数据影响 |
|---|---|---|
| A. 固定 16 + 每次轮换 1 个其他难度 | **96** | 传奇每 30 分钟一个点；其他难度每 8 小时一个点 |
| B. 每次只拉 1 个轮换难度 | **48** | 每个难度每天 3 个点；传奇曲线会变稀 |

配套：
- 启动时 `sleep $((RANDOM % 120))` 打散整点；
- 难度顺序随机；
- 每个请求之间 sleep 1–3 秒；
- 失败不重试整轮，下一轮自然补。

> 趋势曲线还有客户端被动上传兜底；cron 只是补全，没必要 16 难度全量高频。

### 3.2 传输层（不增加请求，减少字节）

#### ⑧ 图片统一走 WebP（1 行改动，7× 收益）

`src/api/config.js` 的 `getImageUrl()` 现在拼 `.png`。资源站同路径 `.webp` 均可用（实测多类资源 100% 命中）：

| 资源 | PNG | WebP |
|---|---|---|
| 角色头 `rolecharacter/roleheadr5sailinna6` | 1,031KB | **145KB** |
| 角色头 `roleheadr7luxiya1` | 631KB | **114KB** |
| 辅助机 `rolepartner/pet3wuya1` | 51KB | **13KB** |
| 头像框 `roleplayersp/headframe27` | 65KB | **14KB** |
| 玩家头像 `roleplayersp/roleheadr5lifu6` | 82KB | **14KB** |

实现：`getImageUrl` 返回 `.webp`；所有 `<img onError>` 统一改成“失败一次后回退 `.png`”，避免个别资源缺 WebP 时裂图。建议抽一个 `<AssetImg>` 组件统一处理。

**收益**：玩家页 55MB → **约 8MB**（仍大，但已降 85%）；首页 9.1MB → **约 1.3MB**。

#### ⑨ 图片懒加载（减少“资源站”请求数）

玩家页 85 张角色卡一次性全部请求；历史弹窗最多 20 周 × 9 张。

- 所有非首屏图片加 `loading="lazy" decoding="async"`；
- 补 `width`/`height` 或 `aspect-ratio`（当前 CLS 0.064–0.085）；
- 角色卡可做 IntersectionObserver 增量渲染（每批 24 张），进一步降低首屏解码。

**收益**：玩家页首屏图片请求 **85 → 约 12**；历史弹窗 **180 → 约 20**。

#### ⑩ 广告图可保留，但换成 WebP + 去掉无限动画

- 1.34MB PNG → WebP 约 80–120KB；
- 删除 `ad-flash` 的 `box-shadow`/`scale` 无限动画；
- 漂动改 `transform: translate3d()`，不要动 `left/top`。

### 3.3 本地处理层（纯性能，与源站无关）

- **趋势采样**：200 条 × 100 人 ≈ 3MB 同步 parse+stringify。改成上限 48 条、先判时间再 parse、IndexedDB 存储；打开曲线弹窗不再重复 parse。
- **fetchJson 缓存**：无上限 `Map` 改 LRU（30 条）+ `inflight` 去重；历史周不驻留内存。
- **弹窗状态下沉**：`RankingPanel` 的 `modal/saTarget` 变化会重建 `rowProps`，导致可见行全部重渲染；把弹窗挂到独立 `ModalHost`，或 `useMemo` 稳定 `rowProps`。
- **CSS**：去掉 `.rankings` 的 `backdrop-filter: blur(24px)`、body 的 `background-attachment: fixed`；`gold-glow`/`medal-gold` 改静态阴影（当前 4–6 个元素永久动画 text-shadow/box-shadow）。
- **导航**：建站时长独立组件或 ref 更新，避免每秒 setState 整棵导航。
- **长列表**：幻痛 100 行可虚拟化；玩家页 85 卡可分页/增量。

## 五、落地顺序

### 阶段 1（半天，低风险，立刻降请求）

1. `getImageUrl` 切 `.webp` + 统一 fallback（先做 `<AssetImg>`）。
2. 玩家页/历史/幻痛图片加 `loading="lazy"` 和宽高。
3. `PlayerPage`/`MinePage` 的元数据改 `/warzone/current`、`/ppc/current`。
4. `fetchJson` 加 `inflight` 去重（并发同 URL 只发一次）。
5. cron 加 jitter + 请求间 sleep（先不改频率）。

### 阶段 2（1–2 天，结构性降请求）

6. IndexedDB 缓存层 + TTL 分级 + stale-while-revalidate。
7. 历史战绩改 `loadPlayerHistory()` 批量接口，结果缓存 24 小时。
8. 我的页回填/重算合并为单次遍历。
9. 对上游请求加串行队列（400–800ms）+ 退避 + 熔断。
10. 跨标签页 `navigator.locks` 协调。

### 阶段 3（可选，流量上来后）

11. cron 降频：16+1 轮换（96/天）或单难度轮换（48/天）。
12. 图片缩略图：Cloudflare Worker / 自建 `/api/img?w=` 代理 + 长缓存（源站无缩放能力）。
13. 边缘共享缓存：Cloudflare Worker 在源站前缓存 60–300 秒，所有访客共享（需实测 Worker 是否被 Cloudflare 403）。
14. GH Actions 每小时快照 16 难度到 Supabase（384/天），客户端读自家 API；流量 >50 访客/天时比“每个访客直连”更省。

## 六、代码骨架

### 6.1 单飞 + 队列 + 退避

```js
// src/api/upstream.js
let chain = Promise.resolve();
let blockedUntil = 0;

const sleep = ms => new Promise(r => setTimeout(r, ms));

export function enqueue(task) {
    chain = chain.then(async () => {
        const wait = Math.max(0, blockedUntil - Date.now());
        if (wait) await sleep(wait);
        await sleep(400 + Math.random() * 400); // 400–800ms 抖动
        return task();
    });
    return chain;
}

export function noteFailure(status) {
    if (status === 403 || status === 429) {
        blockedUntil = Date.now() + 10 * 60 * 1000; // 熔断 10 分钟
    }
}
```

### 6.2 缓存 key 规范

```
huaxu:v1:meta:current
huaxu:v1:wz:{week|current}:{difficulty}
huaxu:v1:player:{id}
huaxu:v1:player-history:{id}
huaxu:v1:ppc:{week|current}:{level}
huaxu:v1:char:{playerId}:{charId}
```

### 6.3 使用方式

```js
// 首页
const data = await cachedJson(`wz:current:${difficulty}`, url, TTL.current);
// 历史周
const data = await cachedJson(`wz:${week}:${difficulty}`, url, TTL.history);
// 元数据
const meta = await cachedJson('meta:current', `${API_CONFIG.warzone}/current`, TTL.meta);
```

## 七、验收指标

1. **每会话上游请求数**：DevTools Network 过滤 `api.huaxu.app`，典型探索（首页→玩家→历史→我的）应 ≤ 8。
2. **首页重复访问**：5 分钟内刷新页面，Network 中上游请求 = 0（frm cache/IndexedDB）。
3. **历史周重复切换**：第二次切同一周 = 0 请求。
4. **玩家页图片**：首屏图片请求 ≤ 15，传输 ≤ 2MB。
5. **cron**：日志中每天请求数 ≤ 96，且时间点不固定。
6. **失败行为**：断网/403 时展示缓存数据并提示“数据可能稍旧”，不出现连续重试。

---

## 八、一句话总结

**先换轻量接口和历史批量（请求数砍 90%），再用 IndexedDB 把 60 秒缓存延长到 5 分钟/永久，最后用单飞+队列+退避把“连发”变成“散步”；图片全部换 WebP 并懒加载。** 这样既不牺牲体验，也不会让源站觉得被爬。
