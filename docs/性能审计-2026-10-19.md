# 性能审计报告（2026-10-19）

> 审计范围：`refactor-react` 分支当前工作区（React 19 + Vite 8 构建产物 `dist-web/`、`api/`、`supabase/`）
> 方法：全量源码走查 + Playwright（系统 Chrome）+ `vite preview` 加载构建产物实测 + 接口响应头核对
> 说明：测量在 headless Chrome（无真实 GPU 合成）下完成，网络为本地回环，所以只采信“体积/请求数/耗时/节点数/动画数”这类结构指标；绘制与合成开销按浏览器渲染常识定级，真机需再用 Performance 面板复核。
> 结论：**功能架构没问题，瓶颈集中在“图片资产”和“数据层重复劳动”两处**——首屏约 10MB 图片（单个角色头像 1MB），玩家页一次查询 55MB；趋势采样每次榜单加载要同步处理 2.4–3MB localStorage；历史战绩 20 周串行 27 个请求耗时 17.6 秒。

## 三、问题详解

### P0-1 角色头像尺寸严重超标（最大问题）

**证据**

- `HEAD https://assets.huaxu.app/cn/image/rolecharacter/roleheadr5sailinna6.png` → `Content-Length: 1056097`，`1024×1024`，PNG。
- 玩家页 85 张卡全部渲染，实测 88 个图片请求、55.1MB。
- 首页桌面 26 张 `assets.huaxu.app` 图片 9.1MB（平均 350KB）。

**定位**

- `src/components/PlayerPage.jsx:29`（角色卡 `<img className="character-icon">`，无 `loading`、无尺寸属性）
- `src/components/PlayerPage.jsx:233`（`acquiredChars.map` 一次性渲染全部 85 张）
- `src/components/Modals/HistoryModal.jsx:36`（历史周角色图标，最多 20 周 × 9 张）
- `src/components/Ranking/RankingRow.jsx:46,50`（榜单行角色/辅助机图标；虚拟滚动减轻了数量，但单张仍 1MB）
- `src/components/Modals/CharacterModal.jsx`、`TeamModal.jsx`、`RankingModal.jsx` 等同源

**影响**

- 首次访问玩家页 55MB；按 4G 5Mbps 约 90 秒，移动流量 55MB。
- 解码内存：1024²×4B ≈ 4MB/张，可见 10–15 张即 40–60MB。
- 图片无宽高 → CLS（0.064–0.085）。

**修复建议（按性价比）**

1. **优先出缩略图**：在 CDN/图片代理上生成 96px（1x）/192px（2x）WebP，榜单 24px 用 48px 图，角色卡 48px 用 96px 图。预计单张 1MB → 3–8KB，玩家页 55MB → **0.5–1MB**。
   - 若无现成缩放服务：`assets.huaxu.app` 在 Cloudflare 后，可启用 Cloudflare Image Resizing（`/cdn-cgi/image/width=96,format=webp/...`），或自建 `/api/img?w=` 代理（Vercel 函数 + sharp，带长缓存）。
   - 退而求其次：构建期把常用角色头像批量转 96px WebP 放 `public/`（角色数量有限，约 100 个）。
2. 角色卡/历史列表加 `loading="lazy" decoding="async"`（`RankingRow` 已有 `decoding`，仍建议补 `loading`）。
3. `<img>` 加 `width`/`height` 或 CSS `aspect-ratio`，消除 CLS。
4. 长列表可加 `content-visibility: auto` + `contain-intrinsic-size`，减少首屏外的布局/绘制。

### P0-2 浮动广告图 1.34MB + 永久动画

**证据**

- `public/img/Snipaste_2026-10-19_15-30-13.png`：1,343KB，974×868，显示 340px。
- 首页同源图片流量 1.34MB，占 97%。
- 截图显示广告悬浮在排行榜正中，遮挡前 3 名内容。

**定位**

- `src/components/AdFloat.jsx:85`（`<img src="/img/...png">`）
- `src/components/AdFloat.jsx:33`（每 2.5s 改 `left/top`）
- `src/styles/app.css:124-135`（`transition: left 2s, top 2s`）
- `src/styles/app.css:202-213`（`ad-flash` 无限动画 box-shadow + `scale(1.03)`）

**影响**

- 首屏最大单文件；移动端流量与解码成本。
- 每 2.5s 触发布局（left/top），动画期间几乎持续合成；`ad-flash` 动画 box-shadow 强制重绘。
- 遮挡内容（UX）。

**修复**

1. 转 WebP/AVIF，340px 宽 2x 图约 60–100KB（-97%）。
2. 删除 `ad-flash` 的 box-shadow/scale 关键帧，最多保留 1 次入场动画；或改为伪元素 opacity 呼吸。
3. 漂动改用 `transform: translate3d()`（只走合成），不要动 `left/top`。
4. 默认位置避开榜单主内容（右下/左下），或首屏 3 秒后再出现。

### P1-1 趋势采样 3MB 同步读写

**证据**

- 200 条 × 100 人 = 3.08MB JSON；浏览器 `setItem` 2.37MB 13.3ms（桌面）。
- `recordCurveSample` 在每次榜单加载执行；即使 60 秒内不写，也要 `JSON.parse` 全量数组。
- 打开趋势弹窗 `getPlayerCurve` 再 parse 一次。
- localStorage 同源还有：`my_wz_last_sync`（area+ppc 原始响应）、`my_wz_scores`（20 周 × 阵容）、`huaxu_roster_*`（每个玩家一份反推缓存），合计容易逼近 5MB 配额；超限后 `catch` 静默，曲线停止记录。

**定位**

- `src/api/storage.js:11-44`（parse → 构造 → 比较 → `slice(-200)` → `setItem`）
- `src/hooks/useWarzone.js:59-62`（每次加载调用）
- `src/components/Modals/CurveModal.jsx:453`（本地曲线再 parse）
- `src/api/storage.js:39`（200 条上限）

**修复**

1. 先判断时间/变化再 parse：把最后采样时间单独存一个 `huaxu_wz_curve_meta_{diff}_{week}`，60 秒内直接 return。
2. 降低上限到 48–72 条（30 分钟采样一天 48 条已足够画当天；历史趋势由后端提供）。
3. 改成“一条采样一个 key”（`huaxu_wz_sample_{week}_{ts}`）或 IndexedDB：写入 O(1)，不再全量序列化。
4. 存储瘦身：`p` 只存 `pid -> [z1,z2,z3,total]`，名字从接口/后端取；可再省 30–40%。
5. 对 `setItem` 失败（QuotaExceeded）做提示/清理旧周，而不是静默。

### P1-2 接口内存缓存无上限

**证据**

- `cache` 是普通 `Map`，写入后只按 60s 判断过期，**从不删除**。
- 单条榜单 215KB；历史战绩 20 周 × 最多 3 难度、16 个难度切换、多周浏览都会累积。
- 历史弹窗一次 20 周即可留下 20–60 条 ≈ 4–13MB。

**定位**：`src/api/client.js:5-19`

**修复**

1. 改成 LRU（上限 20–30 条）或每小时清理过期项。
2. 增加 `inflight` Map 去重并发同 URL 请求（同时解决“我的”页两个 effect 重复请求）。
3. 大响应（`/players/{id}/warzone`、历史周）不缓存，已有 `cache:false` 的用法可推广。

### P1-3 历史战绩串行探测

**证据**：20 周 17.6s / 27 请求。

**定位**：`src/components/Modals/HistoryModal.jsx:134-167`

**修复**

1. **直接用批量接口**：`GET /servers/cn/players/{id}/warzone` 一次返回约 100 周（含段位/排名/分数/三区/阵容），`src/api/history.js` 已封装。冷请求 30–60s，CDN 命中 2–10s；比 27 次串行更可控，且可复用 localStorage 缓存。
2. 若保留探测：每周的 3 个候选难度用 `Promise.all` 并发；去掉 60ms 固定 sleep，改为仅在 429 时退避；结果按周缓存。
3. 进度展示改为“当前周/总周数”，并提供取消（已有 `cancelledRef`）。

### P1-4 我的页回填/重算双链路

**证据/定位**

- 回填 effect：`src/components/MinePage.jsx:478-513`，对每条缺 `mech/monster` 的记录串行 `loadWarzone(diff, week)`。
- 重算 effect：`:517-552`，对每条 `diff` 不匹配的记录串行 `computeWzRanks`，内部再 `loadWarzone` + 3 次 `computeRankingGroups`。
- 两个 effect 都依赖 `[scores]`，`setScores` 后再次触发；同一周可能被两条链路同时请求（缓存尚未写入时无法去重）。
- `computeWzRanks`（`:62-89`）每次对三区各跑一次 `computeRankingGroups(wz.rankings, ...)`（每区 100 人遍历 3 次）。

**修复**

1. 合并为一个 effect、一次遍历；按 `week` 去重，回填与重算共用同一次 `loadWarzone` 结果。
2. 用批量接口拿到该玩家所有周，一次性补齐（与 P1-3 同源）。
3. `computeRankingGroups` 结果按 `week+zone` 缓存，三区一次遍历生成三个 map。
4. 加 `sessionStorage` 标记，已完成补齐的周短期不再重跑。

### P1-5 登录链路重复与串行

**证据/定位**

- `auth.init()`：`src/components/MinePage.jsx:1773` 与 `src/components/MinePage.jsx:691`（WebLoginBlock）各调一次 → 2 次 `GET /api/user-data`。
- `_pushToCloud`：`src/api/auth.js:180-198` 对 7 个 key 串行 `await fetch` → 登录成功到“云端同步完成”要 7 个往返。
- `KuroBlock` 自动同步：`refreshData` → `area` + `prisonerCage`（3 个请求），叠加 `roleList`、`accountData`，进入“我的”页一次最多 5 个请求。

**修复**

1. `auth.init()` 单例 Promise（模块级 `initPromise`），只拉一次。
2. 新增批量 PUT（body 传 `{items:{key:data}}`）或 `Promise.all` 并发（至少把 7×RTT 降为 1×RTT）。
3. 自动同步按 `KURO_AUTO_SYNC_KEY` 已有 10s 防抖，可提升到 60s，并在 `visibilitychange` 时暂停。

### P2-1 无限阴影动画

**证据**

- 首页检测到 6 个 `animation-iteration-count: infinite`：`.rank-medal.medal-1`（`medal-gold`）、3 个 `.zone-max-tag` + 1 个 `.total-max-tag`（`gold-glow`）、`.ad-float`（`ad-flash`）。
- `gold-glow` 动画 `text-shadow` + `box-shadow`；`medal-gold` 动画 `box-shadow`。

**定位**

- `src/styles/ranking.css:248-251, 273-276`
- `src/styles/ranking.css:410-430`（`.zone-max-tag`）
- `src/styles/ranking.css:506-517`（`.total-max-tag`）
- `src/styles/app.css:202-213`（`ad-flash`）

**影响**：这些标签在榜单里出现频率不低（同阵容最高分很常见），等于让可见行持续重绘；`text-shadow` 动画会强制逐帧重栅格化文本，移动端最贵。

**修复**：改成静态阴影/渐变边框；如要“呼吸”，用 `::after` 只动画 `opacity`（合成层），并限制在 1–2 个元素上。

### P2-2 大面积毛玻璃 + 固定背景

**定位**

- `src/styles/ranking.css:2-11`：`.rankings` 整块 `backdrop-filter: blur(24px) saturate(180%)`。
- `src/styles/theme.css:35-38`：body 固定渐变 `background-attachment: fixed`。
- `src/styles/app.css:7-9`、`src/styles/zone.css:100`：导航/弹窗 `blur(8–20px)`。

**影响**：大面积模糊在滚动/动画时每帧重新采样背景；`fixed` 背景在移动端滚动会整屏重绘。两者叠加是移动端掉帧典型来源。

**修复**

1. 榜单面板改用不透明 `var(--surface)` 或极轻的半透明（无 blur）。
2. 去掉 `background-attachment: fixed`，改为 `body` 固定伪元素（`position: fixed; inset: 0; z-index: -1`）避免滚动重绘。
3. 只在导航/弹窗保留小面积 blur。
4. 提供 `prefers-reduced-motion` / 低端机降级（可用 `@media (prefers-reduced-transparency)` 或 JS 探测）。

### P2-3 广告位移与导航每秒重渲染

- `AdFloat`：`left/top` + 2s transition，每次移动触发布局；建议 `transform: translate3d`。同时每 2.5s 读 `offsetWidth/offsetHeight`（强制布局），可缓存尺寸。
- `Nav`：`src/components/Nav.jsx:24-37`，1 秒 `setState` 重渲染整个导航（含 5 个按钮）。建议把“建站时长”拆成独立组件，或直接用 ref 改 textContent；移动端不显示秒。

### P2-4 图片无懒加载 / 无尺寸（CLS）

- `PlayerPage`、`HistoryModal`、`PPC` 的头像 `<img>` 均无 `loading="lazy"`。
- `RankingRow` 有 `decoding="async"` 但无 `loading`（虚拟滚动下影响有限）。
- 无 `width/height`，CLS 0.064（桌面）/0.085（手机）。

**修复**：统一 `<img loading="lazy" decoding="async" width height>`；首屏关键头像可 `fetchpriority="high"`，其余 low。

### P2-5 弹窗状态导致列表重渲染

`RankingPanel` 持有 `modal/saTarget/curveTarget/playerRankTarget`，任一变化都会重建 `VirtualRankingTable` 的 `rowProps`（`src/components/Ranking/VirtualRankingTable.jsx:50-61`），react-window 浅比较失败 → 可见行全部重渲染（含大量图片节点）。建议把弹窗状态下沉到独立 `ModalHost`，或用 `useMemo` 稳定 `rowProps`；`getRankDelta` 每次返回新对象也使 `ZoneCell` 的 `memo` 实际失效，可缓存 delta。

### P3-1 `/api/curve` 取到最旧 200 条

```js
.order('sampled_at', { ascending: true })
.limit(MAX_ROWS)   // 200
```

`order asc + limit` = 最早的 200 条。定时采样每天 48 条，约 4 天就超过 200，之后新采样永远查不到（前端只见旧曲线）。改为 `ascending:false` 取最新 200 条，再在 JS 里 `reverse()`。

### P3-2 `/api/trends` 写放大

- 每次榜单加载，前端 POST 100 行，`sampled_at` 用服务端 `new Date()`；不同访客时间不同，唯一约束无法跨访客去重。
- GitHub Actions 每 30 分钟再写 16×100 = 1600 行。
- 结果：表按访客数线性膨胀，`/api/curve` 的 `limit 200` 更容易被同一分钟的重复样本占满。

**修复**：所有上传者统一用 5 分钟对齐的 `sampled_at`（`Math.floor(Date.now()/300000)*300000`），唯一约束即可跨访客去重；或在服务端按 `(week,difficulty,player,bucket)` upsert；再加个 `week` 单列索引供 cron 清理。

### P3-3 `sessions.token` 索引

`api/user-data.js:28-32` 每次请求 `select ... eq('token')`；`supabase/auth.sql` 只给 `users.player_id` 加了唯一约束，未见 `sessions.token` 索引。用户量大后每次鉴权全表扫描。建议 `create unique index on sessions(token)`，并为 `expires_at` 加索引做清理。

### P3-4 首屏连接与分包

- `index.html` 无 `preconnect`：首次 `api.huaxu.app` 请求实测 470–1088ms（DNS+TLS+Cloudflare）。加：
  ```html
  <link rel="preconnect" href="https://api.huaxu.app" crossorigin>
  <link rel="preconnect" href="https://assets.huaxu.app" crossorigin>
  <link rel="dns-prefetch" href="https://assets.huaxu.app">
  ```
- `vite.config.js` 无 `manualChunks`；当前主包 71KB gz 尚可，Recharts 101KB gz 仅点开分布图时加载（470ms）。可把 `react`/`react-window` 拆 vendor，稳定缓存；优先级低。
- `favicon.ico` 117KB，建议换成 32×32/180×180 的 5–15KB 版本。

## 七、附：优先级判断依据

- **P0**：直接影响首访可用性（几十 MB 流量、移动端解码内存、首屏最大单文件）。
- **P1**：主线程阻塞 ≥50ms 或请求数/时长明显异常（17.6s、3MB 同步 IO、内存无上限）。
- **P2**：持续但单次较小的开销（动画重绘、合成、周期性重渲染、CLS）。
- **P3**：数据正确性/长期成本（曲线截断、写放大、索引缺失、连接预热）。
